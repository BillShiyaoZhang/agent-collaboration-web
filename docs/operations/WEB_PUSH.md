# 浏览器后台推送

Web 提醒中心保存已认证的协作进展；系统提醒只是显示渠道。用户在此设备明确开启后，服务端常驻 worker 可以在网页关闭时向浏览器推送。浏览器仍需支持后台接收、保有当前登录会话及通知权限；关闭页面不等于操作系统允许已退出的浏览器继续运行。[Push API](https://developer.mozilla.org/en-US/docs/Web/API/Push_API)

## 部署要求

| 配置或文件 | 要求 |
| --- | --- |
| `NEXTAUTH_URL` | 实际访问的 HTTPS 地址；本地 HTTP 示例默认不开后台推送 |
| `NEXTAUTH_SECRET` | 保持原值；同时用于加密订阅和 VAPID 私钥，不能随镜像更换 |
| `DATABASE_URL` | 可写持久 SQLite 卷，沿用现有工作台数据库 |
| `WEB_PUSH_SUBJECT` | 可选，发送方的 HTTPS 地址或 `mailto:` 联系地址；默认使用 `NEXTAUTH_URL` |
| `WEB_PUSH_DISABLED=1` | 关闭服务端后台推送；站内提醒仍可用 |
| `WORKSPACE_SYNC_DISABLED=1` | 测试/构建时同时禁止后台同步和推送，不应用于需要推送的生产进程 |
| `public/agent-comm-sw.js` | 必须随发布复制；根路径公开提供，不重定向登录，不长期缓存 |

不需要另购消息队列或手工提交 VAPID 私钥。首次配置查询自动生成一对 VAPID 密钥并加密持久化；进程重启继续使用同一对。VAPID 用于向浏览器推送服务证明发送方，与 agent 的任务授权无关。[web-push 官方说明](https://github.com/web-push-libs/web-push/tree/v3.6.7)

服务端新增 HTTPS 443 出站连接的固定允许范围：`fcm.googleapis.com`、`updates.push.services.mozilla.com`、`web.push.apple.com`、单级子域 `*.notify.windows.com`。不接收任意 URL、私网地址、其他端口或重定向目的地。浏览器还需能访问其厂商的推送服务；服务器能访问 npm 不证明这条链路已通。

升级执行现有 `prisma/remote-console.sql`，追加 `WebPushConfig`、`WebPushSubscription`、`WebPushDelivery` 三张表和索引，不改旧账户、凭据、协作或提醒行。先在一致性 SQLite 备份上验证，再由容器入口应用。用新 schema 生成目标 Linux 平台的 Prisma client。锁文件新增生产依赖 `web-push@3.6.7`；Next standalone 可能将其打入 server chunk，发布检查应同时核对代码打包和运行时文件，不能仅查看 `node_modules/web-push` 是否存在。

## 权限、隐私和投递

- 开启、关闭和测试都从登录后的同源界面操作；服务端只使用会话账号。此设备的订阅不能迁给另一账号，不能借设备 ID 读取其他账号配置。
- 每个账号最多 8 个活动设备。订阅最长有效 30 天，浏览器更短的期限优先；过期后需要用户再次开启。关闭会清除 worker 绑定、取消浏览器订阅并撤销服务端许可。退出登录也执行关闭；下次登录不会静默重新订阅。
- 推送载荷仅有随机投递 ID、随机订阅绑定及期限，通知标题/正文为固定概括，不含人名、消息、授权内容、凭据或可执行命令。展示前 worker 用当前会话向服务器核对账号、绑定、通知版本、未读状态、源状态新鲜度和期限。
- 原有配对读取范围不变，推送不新增 agent 权限。点击仅打开 `/dashboard/notifications`；读取回执、点击或标记已读都不代表同意原生授权。
- 前台有焦点时延后普通系统提醒；页面仍可见但被另一应用盖住时属于离开状态。服务端心跳与 worker 的窗口判断共同处理前后台切换。显式点击“发送测试提醒”可在前台显示。
- SQLite 队列与租约跨进程重启恢复。每项最多 5 次网络尝试，最长 15 分钟，源端超过 2 分钟未重新核验就停止显示。临时发送失败按退避重试；发送被接受但回执丢失，也只重试同一投递 ID。404/410 撤销失效订阅，401/403 停止该项发送并显示诊断。
- 页面通知与 Web Push 共用设备认领表；worker 用 IndexedDB 对每项原子认领显示尝试。重复推送补回已保存回执；已显示状态不会被较晚的前台回执降级。关闭/切换账号的确认等待在途显示完成并关闭，避免旧显示在关闭完成后重新留下条目。

## 测试与诊断

提醒中心提供“发送测试提醒”和诊断详情；测试不建立任务、不批准授权、不读取新的 agent 能力，每设备每分钟最多一次，2 分钟过期。

| 诊断 | 能证明什么 |
| --- | --- |
| 已排队 / 正在发送 | 服务器保存了测试并在尝试发送 |
| 推送服务已接收 | 浏览器厂商接受了投递，尚无浏览器回执 |
| 浏览器已收到 | worker 已通过当前登录和状态核验 |
| 浏览器接受显示请求 | `showNotification()` 成功返回；不证明人看到了横幅 |
| 前台延后 | 页面有焦点，稍后离开时在期限和次数范围内再试 |
| 失败 / 显示失败 / 已过期 | 需检查诊断与当前权限，不应报告成功 |

部署后由用户在目标浏览器开启一次，发送测试并切换应用；再次测试后关闭网页，收到提醒后点击回到中心核对回执。再关闭系统提醒、切换账号，确认旧投递不显示本应用通知。保持站内未读/待处理数据与显示结果分开检查。

自动验证：`npm test` 包含真实临时 SQLite 队列、迁移/账户隔离、重复/过期/重试、前台延后、队列公平性、HTTP 同源鉴权，以及真实 worker 源码配合 IndexedDB 实现的并发显示/关闭测试。`npm run build` 验证生产打包；这些测试不代替浏览器厂商到操作系统的实际投递验收。

## 平台边界与回滚

已显示的概括通知在网页完全关闭后，源端结束不会保证立即从系统通知栏撤回。再次打开页面会核验和关闭旧条目，点击始终读取当前状态。勿将旧系统条目当成仍有效的批准入口。

`userVisibleOnly` 订阅并非无限静默执行通道。Chromium 对可见站点有例外，但后台丢弃重复/失效推送仍可能触发浏览器的概括提示；WebKit 也要求推送产生可见通知。本应用保证同一投递不重复请求展示，不保证浏览器自己的提示完全可控。若目标浏览器表现不适合，应关闭此设备后台推送并使用站内提醒。[Chromium 实现](https://chromium.googlesource.com/chromium/src/+/main/chrome/browser/push_messaging/push_messaging_notification_manager.cc)、[WebKit 说明](https://webkit.org/blog/12945/meet-web-push/)

回滚前备份数据库及原密钥。上一版 Web 可忽略新增表，后台推送会停止；不要删除这些表或重新生成密钥来回滚。浏览器可能还保留已安装 worker 和订阅，旧服务器没有新 API 时它不会显示未核验的本应用通知；重新部署新版本可恢复现存有效配置。若要立即停用，先在新版本撤销对应设备，或设置 `WEB_PUSH_DISABLED=1` 停止新发送，再回滚镜像。已发送到厂商的消息不能可靠召回。
